# 为何 BqLog 如此快之一：从一行文本推导出压缩日志格式

[English](<Article 1_Why is BqLog so fast - High Performance Realtime Compressed Log Format.MD>) · [系列目录](PERFORMANCE_DESIGN_CHS.md) · [下一篇：数据总线](<文章2_为何BqLog如此快 - 高并发环形队列.MD>)

在正式服写日志，我们都想“既要又要”：信息要完整，开销要小，文件还不能太大。尤其在移动设备上，这三件事几乎是互相打架的——记得少，线上问题没法追；记得多，性能和存储又吃不消。

有些日志系统把这个矛盾推给了后处理：先写文本，等文件关闭了再用通用压缩算法压一遍。归档是省了空间，可写日志那一刻的格式化、字符串拷贝、首次写盘，一分钱都没少花，压缩时还得把文件再读一遍。如果我们的目标不是“归档便宜”，而是“详细日志本身就写得便宜”，就得往前再走一步。

这一篇我们就从最普通的一行日志出发，一步步推导出 BqLog 现在的压缩文件格式：哪些内容真的值得写，哪些内容写一次就够。多段结构、加密和恢复也放在同一条线上讲，因为它们都会实打实影响写入成本。

本文参照 BqLog 2.5.0 编写。

## 1. 先看看文本日志到底在做什么

以一个订单系统为例，业务代码可能是：

```cpp
log.info("New order, order ID:{}, price:{}, username:{}",
         32422144, 324.42, "张三");
```

最后落到文件里的是这样一行：

```text
2026-09-25 12:00:00.001 [Info] [Shop.Order] [Tid-2025 Worker25]
New order, order ID:32422144, price:324.42, username:张三
```

为了得到这一行，日志系统至少要把时间戳转成日期字符串，把整数和浮点数转成字符，再把几段固定文本和参数拼起来，最后写文件。如果字符串编码不一样，中间还得多一道编码转换。至于这些活是在调用线程干还是在后台线程干，只是谁来扛成本的问题，活本身一点没少。

紧接着又来了一条订单：

```text
2026-09-25 12:00:00.002 [Info] [Shop.Order] [Tid-2025 Worker25]
New order, order ID:32422145, price:174.45, username:李四
```

问题一目了然：除了时间和三个参数，其他内容一个字都没变，我们却把它重新组织了一遍、重新写了一遍。

一天一千万条这种日志，哪怕每条只有 50 字节是重复的固定内容，光这部分也得写出大约 500 MB。更要命的是，这 500 MB 不只是占地方，它们每一个字节都经历了格式化、拷贝和 I/O。

所以第一步不是去找更厉害的压缩算法，而是利用业务本来就告诉我们的结构：**格式字符串是固定的，参数才是变化的。**

## 2. 不存最终句子，存“怎样拼出这句话”

最直白的做法：第一次见到某个格式字符串，就把它存一份，发个编号。以后再遇到同一个格式，只写编号和参数：

```text
模板 0: New order, order ID:{}, price:{}, username:{}

日志 A: 模板 0, 32422144, 324.42, 张三
日志 B: 模板 0, 32422145, 174.45, 李四
```

看到这里可能有人要问：这不是把格式化推迟到读取的时候了吗？没错，就是这样。关键在于，大量诊断日志写出来之后，放一段时间，过期就被清理了，从头到尾根本没人读。对这部分日志来说，提前拼好完整文本的开销就彻底省掉了。

就算最后真的要读，格式化也可以拿到研发机器或者分析环境里做，没必要让玩家设备扛下所有工作。这是执行时间和执行位置的转移，也是压缩日志赚到的第一笔性能。

但只拆出格式字符串还不够。日志级别、分类、线程 ID、线程名也都在反复出现。把它们一股脑塞进一个大模板，看着省事，却会冒出一个新问题：同一条业务日志由十个线程输出，难道要存十份一模一样的格式字符串？

所以 BqLog 把稳定信息拆成两种模板：

- **格式化模板**：日志级别、分类索引、格式字符串。
- **线程信息模板**：线程 ID 与线程名。

每条日志分别引用这两个模板。线程换了，格式照样复用；业务格式换了，线程信息也照样复用。

分类名还可以继续往外提。对一个 Log 对象来说，它的分类列表是创建时就定死的，所以在文件开头存一张分类表，格式模板里只记一个分类索引。这个思路一路推下去就是一句话：**出现频率越低、生命周期越长的信息，越应该放到外层去。**

## 3. 模板和日志混在一起，读取时怎么分辨

现在我们有三种东西了：格式模板、线程模板、日志记录。它们出现的顺序是不固定的：可能连续写很多条日志，也可能突然冒出一个新线程、一种新格式。

如果为了区分它们，给每种数据单独建一个文件，就得维护好几个文件之间的对应关系，还得处理轮转和异常退出时的一致性，纯属自找麻烦。当前格式把它们串成一串连续的 **Data Item**：每项前面是类型和长度，后面是数据。

![Data Item 的类型位与变长长度](img/performance/compressed-item-bits.png)

<p align="center"><em>图 1：一个 item 的头部和 body，以及两种长度情况下的具体 bit 布局。横向相邻的框在文件中也相邻。</em></p>

为什么还要长度？因为格式字符串和参数个数都不固定。没有长度，就得靠某种结束符一路扫到尾；可二进制参数里什么字节都可能有，结束符还得转义。有了长度，读完头部就知道这一项的范围，也知道下一项从哪开始。

长度直接给 4 字节当然最省事。不过日志往往很短，给一个几十字节的 body 固定配 4 字节长度，怎么看都亏。于是这里引入变长整数编码。

### 3.1 小数字用少量字节

BqLog 用的是带前缀的 VLQ 编码。为了看清楚，先只考虑无符号整数：

```text
1 字节: 1xxxxxxx
2 字节: 01xxxxxx xxxxxxxx
3 字节: 001xxxxx xxxxxxxx xxxxxxxx
...
9 字节: 00000000 + 8 个数据字节
```

前缀里第一个 1 出现在第几位，就告诉 decoder 这个数总共占几个字节。编码变长之后，不再重复表示前一个长度已经覆盖的数字，而是直接从新区间的起点开始计数：

| 字节数 | 起点 | 可表示的区间 |
|---|---:|---|
| 1 | 0 | 0–127 |
| 2 | 128 | 128–16511 |
| 3 | 16512 | 16512–2113663 |

比如 128 不会再在两字节里原样编码成 128，而是表示“第二个区间的第 0 个数”，编码结果是 `40 00`；16512 是第三个区间的第 0 个数，结果是 `20 00 00`。

要提醒的是，这不是 LEB128，光凭 VLQ 这个名字拿别的库是解不出来的，区间起点、前缀和字节顺序都以 [log_utils.h](../src/bq_log/utils/log_utils.h) 为准。不过从性能角度看，收益已经很清楚了：常见的小数只读写一个字节，大数才付更长的编码。

### 3.2 类型只需要一个 bit，凭什么给它一个字节

Data Item 顶层只区分“模板”和“日志”，模板内部再分格式、线程，所以顶层类型只要一位：0 为模板，1 为日志。

照常规做法，一个字节放类型，后面接长度 VLQ，是不是有点浪费？回头看上面的前缀：只要 VLQ 长于一字节，首 bit 一定是 0。这个 0 就可以借给类型用。

比如长度 128 的编码是 `40 00`。如果它是一条日志，把首 bit 置 1，变成 `C0 00`，类型和长度加起来还是只占两字节。

长度 5 的 VLQ 是 `85`，首 bit 已经被长度前缀占了，借不了。这时候才额外写一个字节：日志类型 `80`，长度 `85`，合起来 `80 85`。

decoder 的流程也很直接：先取首 bit 得到类型，再看低 7 位是不是全零。全零就从下一个字节解长度；否则清掉类型位，从当前字节开始解。这样大于等于 128 的 body 复用了首字节，短 body 走显式长度，谁也不亏。

当前 body 长度是 uint32，所以 item 头实际占 2–5 字节。注意长度不包括头本身，这一点在回填和解码时都得保持一致。

## 4. 再把模板里的每一项拆开

![格式模板、线程模板、日志记录和参数的连续布局](img/performance/compressed-templates.png)

<p align="center"><em>图 2：从模板到单个参数逐层展开。颜色对应内容种类，字段中的字节数对应实际编码。</em></p>

格式模板的 body 依次是：

```text
subtype (1 B) | level (1 B) | category_index (VLQ) | format bytes
```

subtype=0 表示格式来自 UTF-8，subtype=2 表示来自 UTF-16，后者在文件里用 UTF-Mixed 表示（第 6 节细讲）。格式字符串占满 body 剩下的空间，所以不必再存一个字符串长度，也不需要结尾零字符。

格式模板的索引也不用写。文件里第一次出现的格式模板就是 0 号，第二次就是 1 号，依次往上排；writer 和 decoder 按相同顺序数就行。这又省掉一个字段，解码端还能直接用数组按下标访问，连哈希表都省了。

线程模板稍有不同：

```text
subtype=1 (1 B) | thread_template_index (VLQ) | thread_id (VLQ) | thread_name
```

这里显式写索引，是因为线程信息可能在新的运行里被重新定义。一个明文文件可能被同一个程序多次打开续写，但上一次的线程 ID、线程名对应关系不能直接套到这一次。新的线程模板可以覆盖某个索引的定义，decoder 按文件顺序更新映射，后面的日志引用新信息。

这里还有一个容易混淆的点：**模板的文件索引不等于内存缓存的槽位。**为了限制长期运行的内存占用，writer 的模板缓存会淘汰条目。被淘汰的格式再次出现时，就再写一份模板、领一个新的文件索引，旧记录照样有效。缓存淘汰影响的是复用率和文件大小，不会把旧文件内容改掉。

至于哈希，文件里也不需要存。哈希是给 writer 快速判断“这个格式见没见过”用的，decoder 靠文件索引就能定位模板。只在运行时加速用的字段，没必要带进磁盘。

## 5. 每条日志真正变化的内容，还能继续压缩

模板抽走之后，日志记录的 body 只剩下：

```text
时间差 | 格式模板索引 | 线程模板索引 | 参数0 | 参数1 | ...
```

两个索引从小数字开始，用 VLQ 很自然。时间戳和参数则值得再多分析一下。

### 5.1 时间戳很大，时间差很小

毫秒级 Epoch 时间要 64 位表示，逐条存就是 8 字节。可连续两条日志的间隔往往只有几毫秒，甚至同一毫秒里好几条。既然上一条时间已知，下一条只记差值就够了。

比如三条日志的时间分别是 1000、1002、1001 ms，差值就是 1000、2、-1。第一条以 0 为基准，后面每条以前一条为基准。

为什么第三条会比第二条小？不一定是系统时钟回拨。多个生产者的数据是按总线轮询进文件的，来自不同线程的记录，本来就可能和时间顺序不一致（第二篇会细讲）。所以这里不能只编码正差值。

ZigZag 正好解决小负数的问题：

```text
原值:     0  -1   1  -2   2  -3   3
映射后:   0   1   2   3   4   5   6
```

把有符号值映射成无符号，再做 VLQ。这样 +1 和 -1 都很小，不会因为负数补码的高位全是 1，被迫占满 8 或 9 个字节。

### 5.2 整数不必转成字符，浮点也不必提前格式化

参数前面存一个类型字节，告诉 decoder 后面该读几字节、要不要解 VLQ：

| 参数 | 去掉类型字节后的内容 |
|---|---|
| null | 不需要内容 |
| pointer | 统一 8 字节 |
| bool、char、int8、uint8 | 1 字节 |
| char16、char32、uint16、uint32、uint64 | 无符号 VLQ |
| int16、int32、int64 | ZigZag + VLQ |
| float / double | 原始 4 / 8 字节 |
| UTF-8 字符串 | 字节长度 VLQ + 内容 |
| UTF-16 字符串 | 转成 UTF-Mixed 后保存长度与内容 |

为什么浮点数不也转成某种变长整数？因为浮点的位模式和数值范围跟整数完全两码事，最终文本还涉及精度格式。直接存二进制值，既省掉当前的十进制格式化，又把还原文本需要的信息完整留了下来。

那为什么 bool、int8 这些小类型反而固定一字节？它们本来就只有一个字节，再套一套编码也不会更省。压缩设计不是教条地给所有东西上同一个算法。

每条记录也不再单独存参数个数。按类型读完一个参数，看看是否到了 item 末尾，就知道了。

## 6. UTF-16：性能与体积之间再做一次取舍

C#、Java、Unreal 经常用 UTF-16。对 ASCII 字符来说，每个字符的高字节都是 0，两字节存一个英文字母确实浪费。但把 UTF-16 无条件转成 UTF-8，遇到中文、代理对和混合文本时判定会变多，而且有些字符的 UTF-8 表示反而更长。

能不能先拿最容易拿的收益？UTF-Mixed 就是这个思路：前面的 ASCII 尽量收窄成一字节，后面一旦不适合继续快速处理，就插一个 `FF` 标记，剩下的 UTF-16 直接整块拷贝。

![UTF-Mixed 的原始字节与编码后字节](img/performance/compressed-utf-mixed.png)

<p align="center"><em>图 3：以标量切分为例，<code>abc中x</code> 的 10 个 UTF-16 字节变成 8 字节。末尾 x 仍留在 UTF-16 后缀里。</em></p>

注意这里的“剩余”包括后面再出现的英文字符——不会为了省一个字节反复切回来。SIMD 路径还可能在包含非 ASCII 的块之前停手，所以相同内容的合法切分不必完全一致。

这个例子如果完整转 UTF-8，只要 7 字节；UTF-Mixed 反而用了 8 字节。那它图什么？图的是编码成本。我们本来就不只追求文件最小，用一个额外字节换后缀的批量拷贝，往往比逐字符完整转换更划算。

decoder 在已知长度里找 `FF`，前缀直接拷贝，后缀转 UTF-8。这里的 FF 不是字符串结束符，而是明确的编码切换标志。至于前面那段收窄怎么用 SIMD 跑，第三篇再讲。

## 7. 同一条日志，在内存和文件里为什么完全不同

讲到这里，很容易冒出一个念头：既然文件格式这么紧凑，干脆让生产者直接构造这种紧凑格式，再交给后台？

问题是，文件模板索引要由对应的 Appender 来分配，多个输出的模板集合还可能不一样。让每个生产者都去碰这套共享字典，等于把后台的状态管理拽进了调用线程。而且为省磁盘设计的变长字段，会增加内存中定位参数的成本。

所以 BqLog 的总线记录保留固定头部和适当对齐，消费端再转成紧凑的文件表示。用一条很小的日志看得最清楚：

```cpp
log.info("hp={}", int32_t(42));
```

![同一条记录的内存表示和七字节文件表示](img/performance/compressed-record-example.png)

<p align="center"><em>图 4：格式为 hp={}，线程名为 Main。图上方是总线内的记录，下方是模板已存在且时间差为 0 时的文件记录。</em></p>

内存头有 40 字节：完整时间戳、分类、线程 ID、格式哈希和长度都在里面。5 字节的格式内容按 4 字节边界对齐成 8 字节，int32 参数占类型区和数值区，最后还有线程扩展信息。这个例子的内部记录共 61 字节，走 LP 路径还会加上 context 和 ring 的块头（第二篇的主角）。

文件里则可以只有：

```text
80 85 | 80 | 80 | 80 | 0B D4
类型/长5  Δt=0 fmt0 thread0 int32(42)
```

0B 是 int32 类型，42 经 ZigZag 得到 84，编码为 D4，整项共 7 字节。文件头和模板另存，由后续记录一起分摊。两套布局的分工一目了然：内存里图的是生产消费顺手，文件里图的是紧凑。

## 8. 一条数据流之外，为什么还需要多段结构

前面讲的是一条连续的数据流：程序一直运行，内存里的模板表和加密状态都在，接着写就行。可程序重启之后呢？

先把一个前提说清楚：**压缩日志的续写，需要知道前面写过什么。**这跟打开一个文本文件、把指针挪到末尾、再写一行字符串，完全是两回事。

### 8.1 续写要恢复的，不只是文件位置

假设旧文件里已经有三条格式模板，编号 0、1、2。新日志又用到其中一种格式，我们得找到它原来的编号；来了新格式，也得知道下一个编号从 3 开始。日志存的是时间差，所以最后一条日志的时间戳也得恢复。

如果完全不读前面的内容，直接把模板编号从 0 重新开始，decoder 却还沿用旧字典，同一个编号就有了两种含义，后面的参数到底该代入哪条格式，就彻底说不清了。

对明文压缩文件，解决办法很直接：打开时扫描一遍已有 item，恢复格式模板表、下一个模板编号和最后的时间戳，然后接着写。线程信息按本次运行重新建立。UTF-16 格式在文件里是以 UTF-Mixed 存的，扫描时还要恢复它原始表示的哈希，后面才能继续查找和复用。

### 8.2 加密文件的问题：写入端手里没有私钥

加密模式下，客户端只配置公钥，私钥既不随客户端分发，也不存在日志文件里。公钥能用来保护新生成的加密材料，却解不开旧文件的内容。

于是刚才那个“扫描旧文件”的步骤直接卡死：**读不出旧模板，就不知道前面用了哪些编号；读不出最后一条日志，时间基线也恢复不了。**同理，旧 payload 用的加密材料，也没法凭公钥重新解出来。

旧状态既然拿不回来，那就重建一套：模板从头记，时间基线重新开始，加密材料重新生成，再写新的 payload。写入端不需要持有私钥，更不需要为了追加几条日志，把整个旧文件解密重写一遍。

这说明文件必须能区分不同的加密 payload，不能假设从头到尾永远共享同一套加密状态。BqLog 用 Segment 描述这样的数据范围，每段有自己的头部和可选加密材料。这里有两个层次，别混了：**重新建立模板状态，开始的是一条新的压缩数据流；生成新的加密材料，开始的是一个新的加密段。**它们经常一起发生，也可能在恢复时分别处理。

在 2.5.0 的普通重启写入流程里，新压缩数据流会放到新编号的文件里，模板表和时间戳随之重置。已有文件内的多段结构则负责把恢复数据和新数据接起来，下面接着看它的布局。

![文件、Segment 和各级头部的字节布局](img/performance/compressed-file-v10.png)

<p align="center"><em>图 5：第一条横条接着第二、第三条，换行只是为了展示。S0、S1、S2 是绝对文件偏移，不是内存指针。</em></p>

外层 File Header 固定 8 字节：版本 4 字节、文件格式 1 字节、padding 3 字节。压缩格式当前是 version=10、format=2。

每段先写 12 字节 Segment Header：

```text
next_seg_pos: 8 B | seg_type: 1 B | enc_type: 1 B | padding: 2 B
```

`next_seg_pos` 指向下一段在文件里的绝对偏移，最后一段用 UINT64_MAX。这样 decoder 不必扫描当前段里的全部 item，就能知道本段在哪结束；按当前段范围读缓存，也防止一次读取跨过段头、误用下一段的加密状态。

`seg_type` 区分普通数据、Appender 缓存恢复、总线恢复。它不是在每条日志头里重复加来源字段，而是在整个阶段变化时记一次。首段 payload 还保存 52 字节元数据和分类定义，后面的段不用再重复这些文件级信息。

段头既不重复存文件级分类表，也不会自动清空模板字典。这样恢复时可以给一批数据换上新的加密材料，同时让它继续用前面已经写下的模板。

### 8.3 先追加新段，再把前段指向它

在文件尾追加一段时，当前实现先检查段链是否有效，再写新段头和必要的加密材料，最后修改旧末段的 `next_seg_pos`。主体日志数据没有被搬来搬去，动的只是链接关系。

这很像单向链表的尾部连接，只不过节点用文件偏移表示。用绝对偏移，关掉程序重新打开还能继续解释，也不依赖这次映射到了哪个虚拟地址。

追加段要检查段链、写头和密钥材料，还要做相应 I/O。这份成本放在文件创建、恢复和状态切换时付一次，后面大量日志共同摊薄它，不用逐条重复。

### 8.4 为什么恢复数据还需要单独的段

异常退出时，日志可能停在不同阶段：一部分还在数据总线里没编码；另一部分已经变成压缩 item，留在 Appender 的映射缓存里没写完文件。

已经编码的缓存，里面的模板编号和时间差属于原来的数据流。恢复这批字节时，不必先解开旧文件再把它们全部重新编码：在经过校验的原文件后面追加恢复段，生成新的加密材料，把缓存内容写进去就行。decoder 持有私钥，按顺序读完旧段后已经建立了模板和时间状态，到新段切换加密材料，就能继续解释这些 item。

总线里还没编码的记录则不同，它们还保留着原始格式和参数，可以交给新的压缩输出重新建立模板。在加密重启场景里，这条路径使用新文件，恢复完成后再进入普通写入阶段。

所以，新段不一定等于新字典。分段把加密状态、数据来源和模板状态的关系表达清楚了，恢复才能直接处理手里已有的数据，避免不必要的整文件读取和重写。

## 9. 加密怎么放，才不会把省下的时间又花回去

说到加密，不能甩一句“用了 RSA 和 AES”就完事，因为这两类操作的成本和作用完全不同。每条小日志都走一次公钥运算，固定成本会反复发生；为了加密先复制出另一份完整缓冲，又平白多一轮内存读写。

当前实现把加密分成两层：

1. 段创建时生成 AES-256 密钥和 IV，用 RSA-2048 保护 AES 密钥，再用 AES-CBC 加密一个 32 KiB 的掩码块。
2. 持续写入时，payload 在 Appender 的批量缓存里，按文件位置与掩码块循环异或。

![每段加密材料与逐批 payload 的实际布局](img/performance/encryption-segments.png)

<p align="center"><em>图 6：上半部分是每段的一次性准备，下半部分是 payload 的常规处理。注意两部分的执行频率完全不同。</em></p>

加密材料占 33048 字节：公钥指纹 8 字节、RSA 密文 256 字节、IV 16 字节、掩码密文 32768 字节。假设一段只有 1 KiB 内容，这份固定材料比正文还大；一段有几十 MiB，它才被摊薄。所以评价加密格式不能只看每字节处理速度，还得看段创建频率和数据规模。

payload 路径按文件偏移算：

```text
mask_index = file_offset & (32768 - 1)
data[i] ^= mask[(file_offset + i) & (32768 - 1)]
```

32768 是 2 的幂，取模可以用位与。不同批次从自己的绝对文件位置出发，不用把“上次处理到掩码哪里”这种隐式状态串起来。按块处理时可以用 SSE、AVX2 或 NEON，循环里载入数据和掩码，异或，写回。

Appender 还会调整缓存 padding，让数据地址和掩码位置满足相对对齐关系，减少非对齐处理的麻烦。写出不完整时，缓存里没写完的部分要恢复成可继续处理的状态——不能让下一次 flush 把已经变换过的内容又当明文处理一遍。

这条热路径便宜，靠的是批量循环异或。它使用重复掩码，没有 AEAD 认证标签；需要防篡改认证的场景，得另外想办法。

## 10. 写入和读取，分别把成本放在哪里

把前面的步骤串起来，一条新日志到达压缩 Appender 时，大致经历：

```text
取格式哈希、级别、分类
  → 查格式模板；未命中则写新模板
  → 查线程模板；未命中则写线程定义
  → 时间差 ZigZag / VLQ
  → 编码模板索引与参数
  → 回填 item 长度
  → 标记本条记录已完整写入缓存
```

长度为什么是回填的？因为 UTF-Mixed 和变长整数的结果长度，要写完才知道。先精确量一遍再写一遍，等于把活干两次；所以这里先按最大空间估一段，写完了回填。第三篇会展开讲这一步怎么避免搬动已经写好的正文。

读取则反过来：打开容器，恢复段状态，加载分类表；遇到格式模板就追加到数组，遇到线程模板就更新映射；遇到记录就还原时间和参数，再调用公共 layout 生成文本。格式化挪到了这里，频繁写入的那一端不再逐条生成完整文本。

当然，代价也跟着挪到了读取端：二进制内容没法直接用文本工具看，从文件中间开始读也不一定有字典和时间基线。writer 缓存有上限，不代表 decoder 要保留的历史模板也有同样的上限。文件轮转既控制磁盘，也影响打开和解码的成本。

## 11. 看结果时，要把完整文件和完整流程算进去

公开 README 的 400 万条体积用例里，BqLog 文本为 302 MB，压缩为 45 MB，约为前者的六分之一。这是那组内容测出来的结果，不是格式承诺的固定比例。如果每条日志的模板都不一样，或者参数本身就是高熵的大块数据，模板复用的收益自然会变。

同样，写入 benchmark 也要看完整：多少线程、最后是否 flush、加密段初始化算不算进去、比较的是文本还是压缩。设计的价值在于减少了重复工作，具体少多少，得让实际内容和测量来回答。

这篇把磁盘上的表示讲清楚了。下一篇回到内存，看看大量生产者怎样把日志交给消费者，而不至于把省下来的格式化成本，又变成另一种线程竞争。
