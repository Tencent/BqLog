# Benchmark

[← 返回首页](../README_CHS.md) | [English](./BENCHMARK.md)

BqLog 面向真实的业务场景：日志写真实的磁盘文件，缓冲区默认固定大小、写满阻塞，一条不丢；需要时可以开启扩容，突发过后内存会回收；支持崩溃后复盘；消费线程默认空闲时休眠以节约CPU资源，用户不用调任何参数。

日志系统不是业务的核心。一个日志库就算单次调用很快，如果为此占用了大量 CPU，或者让内存无限增长，它就不合格。所以这里的每一项结果都同时给出 CPU 消耗和内存。

- **第一部分：吞吐**。所有线程写完、全部落盘为止的总耗时和 CPU 消耗。这是日志给整台机器带来的真实负载。
- **第二部分：日志线程延迟**。业务线程调用一次日志要花多久。

BqLog 的 C++ 数据都使用快速模式（`BQ_LOG_FAST_INFO` 等宏），与普通模式的对比见第 4 节。

## 2. 第一部分：吞吐

### 测试用例

- 1、2、4、6、8、10 个线程同时写，每线程 2,000,000 条，计时从第一条开始，到全部刷到磁盘为止；所有库都用阻塞策略，不丢日志。
- 两条日志：`"idx:{}, num:{}, This test, {}, {}", t, i, 2.4232f, true`（4 个参数），以及 `"Empty Log, No Param"`（无参数）。
- **固定缓冲区**：BqLog 默认配置（每线程 64 KB，写满阻塞）；quill 用 `BoundedBlocking`，每线程 64 KB（Windows 上把它队列满时的重试间隔设为 0：quill 默认的 800 ns 在 Windows 上会变成 `Sleep(1)`，整整 1 毫秒）；fmtlog 开 `FMTLOG_BLOCK=1`；spdlog 异步，8192 槽、阻塞；glog 同步；Log4j2 AsyncLogger。
- **可扩容**：BqLog `log.buffer_policy_when_full=expand`；quill 默认的 `UnboundedBlocking` 队列。其他库没有可以扩容的队列，不参加这一组。
- 消费线程：BqLog 用默认策略，不做任何设置；其他库按各自官方 benchmark 或文档推荐的写法配置，其中 quill 是 0 等待 spin（`sleep_duration=0`，实际业务情况肯定不可能如此）。
- BqLog 分别测了压缩和文本两种输出。压缩+加密的数据和不加密几乎没有区别（总耗时和 CPU 多 2%～15%，多线程时在 5% 以内），为了排版没有列进表里。
- CPU 消耗用 **CPU 时间**表示：整个进程所有线程的 CPU 时间之和，即完成这项工作一共花掉了多少 CPU。这里每个库做的是同样多的工作，所以 CPU 时间可以直接比较；如果改用"CPU 占用率"（CPU 时间 ÷ 总耗时），越快做完的库占用率反而越高，会产生误导。第二部分里日志线程按固定节奏写，各库运行时间相同，所以那里给的是消费端的 CPU 占用率。
- 峰值内存是进程物理内存的最高水位（macOS `phys_footprint`，Windows `PeakWorkingSetSize`）；每个 BqLog 配置单独一个进程。
- BqLog、quill、fmtlog 跑 3 轮取中位数；spdlog、glog、Log4j2 跑 1 轮（spdlog、glog 只跑到 6 线程）。

#### 结论

- **固定缓冲区（默认配置）**：在所有线程数、两种日志下，BqLog 的总耗时和 CPU 时间都是所有库里最低的。4 个参数时，与每个线程数下表现最好的其他库相比：BqLog 压缩快 6.5～8 倍，CPU 时间少到 1/4.9～1/7.2；BqLog 文本快 1.6～1.9 倍，CPU 时间少 16%～42%。BqLog 的峰值内存不超过 3.1 MB。
- **可扩容**：与同样可以扩容的队列相比，BqLog 压缩快 7～8 倍，CPU 时间只有 1/3.4～1/5.7；BqLog 文本快约 2 倍，CPU 时间少 25%～34%；峰值内存约为一半。
- 压缩格式约为文本的 1/7。

## 3. 第二部分：日志线程延迟

### 测试用例

所有库用同一份源码、同一种计时方式：

- 每个日志线程写一批 20 条，批与批之间随机忙等 2000～2200 µs；每线程 5,000 批。
- 每批前后各读一次序列化的硬件计数器（arm64：`isb; mrs cntvct_el0; isb`，x86-64：`lfence; rdtsc; lfence`），每条延迟 = 批耗时 ÷ 20。
- 日志调用写成 lambda，内联进计时循环，和用户代码里的调用点一样。
- 所有库都用固定大小、写满阻塞的队列（每线程 64 KB）；消费线程空闲时都休眠 1 ms（BqLog `log.worker_interval_ms=1`，quill `sleep_duration=1ms`，fmtlog 轮询间隔 1 ms）。
- 指标：**p50**（典型的一次调用）、**p99 / p99.9**（最慢的 1% / 0.1%）、**平均**（日志调用总耗时 ÷ 调用次数，即日志一共占了业务线程多少时间）；同时给出消费端 CPU（日志线程以外所有线程的平均 CPU 占用，按占一个核的百分比）和峰值内存。
- 交替跑 5 轮取中位数。Mac 的硬件计数器精度约 41.7 ns，平摊到每批 20 条后，每条的分辨率约 2 ns；Windows 机器的 TSC 精度远小于 1 ns。

## 4. 快速模式与普通模式

BqLog 的 C++ 有两种写日志的方式，输出完全一样：

- **普通模式**：`log.info("idx:{}", i)`，所有语言的 wrapper 都支持，IDE 代码提示最好。
- **快速模式**：`BQ_LOG_FAST_INFO(log, "idx:{}", i)`，只有 C++ 版本才有。每个调用点绑定第一次调用时的 log 对象和格式串（[详见这里](API_REFERENCE_CHS.md#fast-mode)）。

| | 快速模式 | 普通模式 |
|---|---|---|
| macOS：吞吐，固定缓冲区，4 个参数（总耗时和 CPU 时间） | 与普通模式相差 ±8% 以内 | 基准 |
| macOS：吞吐，固定缓冲区，无参数（总耗时和 CPU 时间） | 文本基本相同；压缩在 1 线程时多 62%，2 线程多 28%～45%，4 线程及以上多 3%～17% | 基准 |
| macOS：日志线程，1 线程（p50 / p99 / 平均，ns） | 4 / 29 / 6.3 | 12 / 60 / 16.2 |
| macOS：日志线程，4 线程（p50 / p99 / 平均，ns） | 6 / 166 / 19.2 | 16 / 181 / 26.9 |
| Windows：吞吐，固定缓冲区，4 个参数（总耗时和 CPU 时间） | 文本相差 ±12% 以内；压缩在 1、2 线程时少 25%～50%，4 线程及以上相差 -20%～+11% | 基准 |
| Windows：吞吐，固定缓冲区，无参数（总耗时和 CPU 时间） | 文本相差 -14%～+3%；压缩在 1、2 线程时少 40%～50%，4 线程及以上相差 -15%～+4% | 基准 |
| Windows：日志线程，1 线程（p50 / p99 / 平均，ns） | 8 / 53 / 12.1 | 37 / 162 / 49.9 |
| Windows：日志线程，4 线程（p50 / p99 / 平均，ns） | 9 / 46 / 12.8 | 43 / 160 / 54.1 |

两种模式的吞吐基本相同：快速模式在日志线程上省下的工作，不会转嫁到消费线程上（例外是无参数的压缩输出，线程少时快速模式略慢）。区别主要在日志线程上，快速模式每次调用快约 8～10 纳秒，在实际业务中几乎可以忽略。

开启扩容时，快速模式的吞吐明显更好（多线程时普通模式的总耗时是快速模式的 1.5～3.7 倍），需要扩容的场景建议使用快速模式。

本版本（2.6.0）的完整工程在 [`benchmarks/2.6.0`](https://github.com/Tencent/BqLog/tree/benchmarks/2.6.0/benchmark/cross)：CMake + FetchContent，每个库一个可执行文件，运行脚本、原始数据，以及生成这些表格和图表的 `make_tables.py`。其他版本的 benchmark 见 [`benchmark` 分支的索引](https://github.com/Tencent/BqLog/tree/benchmark)。
